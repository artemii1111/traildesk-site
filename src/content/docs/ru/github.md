Команда работает в репозитории GitHub как обычно. TrailDesk читает задачи (issues), пулл-реквесты, ветки и выкладки,
а пишет задачи, комментарии и метки, когда заказчик что-то делает на странице или в чате.

## Токен

Создайте **fine-grained personal access token** (GitHub → Settings → Developer settings → Fine-grained tokens)
для репозиториев ваших проектов:

| Разрешение | Доступ |
|---|---|
| Issues | Read and write |
| Pull requests | Read and write |
| Contents | Read |
| Metadata | Read (включено всегда) |

Укажите его в «Пространство» → «Доступ к GitHub» (общий для всех проектов) или в разделе проекта «Репозиторий».

## Вебхук

В разделе проекта «Репозиторий» показаны адрес вебхука и секрет. В репозитории на GitHub: **Settings → Webhooks →
Add webhook**:

- Payload URL — адрес из настроек (`https://<domain>/<project>/api/backlog/github-hook/`);
- Content type — `application/json`;
- Secret — секрет из настроек;
- Events — *Issues, Issue comments, Labels, Milestones, Pull requests, Pull request reviews, Pushes, Branch or tag
  creation, Branch or tag deletion* (или «Send me everything» — остальные события TrailDesk пропускает).

Без вебхука страница всё равно пересобирается раз в 20 минут и по кнопке «Обновить».

## Метки

Страница показывает задачи с меткой `бэклог` и определяет их статус по меткам и следам в GitHub.
Служебные метки пока фиксированные (настраиваемые метки на других языках — [задача #18](https://github.com/artemii1111/traildesk/issues/18)):

| Метка | Что значит |
|---|---|
| `бэклог` | задача видна на странице заказчика |
| `решение` | ждёт решения заказчика |
| `ждём` | ждём кого-то со стороны |
| `взята`, `проверить`, `проверено` | этапы, когда работу не видно в коде |
| `срочно`, `важно`, `после-запуска` | срочность |
| `bug`, `enhancement`, `дизайн`, `контент` | тип задачи |

Области (разделы), хэштеги, команды бота и особая метка «от руководителя» настраиваются для каждого проекта
в «Настройках».

## Как определяется статус

Статус никто не ставит руками — кнопки на странице меняют те же самые метки. Правила проверяются сверху вниз,
срабатывает первое подходящее:

| Статус | Когда |
|---|---|
| Ждёт решения · Ждём других | метка `решение` или `ждём` — главнее всего остального |
| На сайте | задача закрыта, её коммиты вошли в боевую выкладку |
| Проверена | кто-то нажал «Проверено», или задача закрыта, но ещё не выкачена |
| Сделана | код уже в `main`, задача ещё открыта («не проверена N дн.» через два дня) |
| Взята | открыт PR или есть ветка с номером задачи («застряла», если 3 дня нет коммитов) |
| В очереди · Новая | следов работы нет («новая» — заведена за последние 2 дня) |

Та же таблица есть на странице в разделе «Как считается статус».

## Выкладки («На сайте»)

Чтобы понять, что уже на боевом сайте, TrailDesk сейчас смотрит, в таком порядке:

- успешные запуски workflow GitHub Actions с именем **`Deploy`**, у которого задание называется вроде `prod ← sha-<commit>`;
- журнал выкладок (`manage.py backlog_record_deploy sha-<commit>` на сервере TrailDesk);
- голову самой свежей ветки `release/*` — переносите её на выкаченный коммит после каждой выкладки.

Без всего этого задачи останавливаются на «Проверена» / «Сделана». Более простой и общий способ сообщать о выкладках
(GitHub Deployments, релизы или вебхук) запланирован — [задача #22](https://github.com/artemii1111/traildesk/issues/22).
